# บัญชีเว็บหวย (lotto-accounting)

เว็บแอปสำหรับบันทึก **เงินเข้าเว็บ** (สลิปโอน) และ **เงินออกจากเว็บ** (แคปหน้าจอถอนสำเร็จ)
กรอกผ่านฟอร์มใน LINE (LIFF) — เลือกเว็บจาก dropdown แล้วอัปโหลดรูป
ระบบถอด **เลขที่รายการและธนาคาร** จาก QR ตรวจสอบสลิปเองในเครื่อง และอ่าน **วันที่กับยอดเงิน**
จากตัวหนังสือด้วย Google Cloud Vision แล้วเก็บลง Supabase
ดูสรุปยอดรายวัน / รายเดือน / รายเว็บ ได้ทั้งในเว็บและในแชท LINE

อัปโหลด **ภาพหน้าฝาก/ถอนของเว็บคู่กับสลิปธนาคาร** ทีละหลายคู่ก็ได้ — ระบบแยกเองว่าใบไหนเป็นอะไร
จับคู่ให้ตามยอดเงินกับเวลา แล้วเติมชื่อเว็บ บัญชีที่โอนออก และบัญชีปลายทางให้ครบ

## ฟีเจอร์

| ส่วน | รายละเอียด |
|---|---|
| แยกผู้ใช้ | หนึ่ง LINE account = หนึ่งชุดข้อมูล ไม่ปนกัน ล็อกอินด้วย LINE Login |
| อนุมัติสมาชิก | คนที่เข้ามาใหม่ต้องรอผู้ดูแลกดอนุมัติที่หน้า `/admin` ก่อนถึงใช้งานได้ |
| สิทธิ์ดูข้ามบัญชี | ผู้ดูแลเลือกได้รายคนว่าให้เห็นเฉพาะบัญชีตัวเอง หรือเห็นสรุปยอดของทุกคน |
| บันทึกรายการ | เลือกประเภท (เข้า/ออก) → เลือกเว็บจาก dropdown → อัปโหลดรูป → ตรวจค่าที่อ่านได้ → บันทึก |
| อ่าน QR บนสลิป | ถอดเลขที่รายการและธนาคารต้นทางจาก QR ตรวจสอบสลิปเองในเครื่อง ไม่ต้องเรียก API ใด ๆ |
| อ่านรูปอัตโนมัติ | อ่านยอดเงิน วันเวลา เลขอ้างอิง ธนาคาร และชื่อเว็บ พร้อมแปลง พ.ศ. → ค.ศ. ให้เอง |
| ค่าใช้จ่ายต่ำ | QR อ่านเองในเครื่องฟรี ส่วน Vision ฟรี 1,000 ภาพแรกต่อเดือน |
| อัปโหลดเป็นคู่ | โหมด "หน้าเว็บ + สลิป" ในหน้าบันทึกรายการ รับทีละหลายคู่ จับคู่ให้เอง แล้วกดบันทึกทั้งหมดทีเดียว |
| อ่านหน้าเว็บ | อ่านโดเมน ยอดที่แจ้ง บัญชีที่โอนออก/ปลายทาง พร้อมชื่อเจ้าของบัญชี และรหัสรายการของเว็บ |
| กันบันทึกซ้ำ | เช็ค sha256 ของไฟล์ เลขที่รายการจาก QR และรหัสรายการของเว็บ — ครอปหรือบีบอัดใหม่ก็ยังจับได้ |
| แก้/ลบได้ | หน้ารายการแก้ยอด วันที่ เว็บ ประเภท และลบพร้อมรูปได้ |
| สรุปยอด | วันนี้ / เมื่อวาน / 7 วัน / รายเดือน / ทั้งปี แยกตามวัน เดือน และเว็บ |
| สรุปใน LINE | พิมพ์ `สรุป`, `เดือนนี้`, `08/2569` ฯลฯ ในแชท แล้วบอทตอบเป็นการ์ดสรุปยอด |
| จัดการเว็บ | รายชื่อเว็บใช้ร่วมกันทั้งระบบ ใครเพิ่ม/แก้/ปิดใช้ ทุกคนเห็นเหมือนกัน ตั้งสีและอิโมจิประจำเว็บได้ |
| ผูกโดเมน | อ่านโดเมนจากภาพ (เช่น `kindee365.com`) แล้วเลือกเว็บให้เอง ยังไม่มีก็เพิ่มเว็บนั้นให้อัตโนมัติ |

**เงินเข้าเว็บ** แสดงด้วยสีแดง (เงินออกจากกระเป๋าเรา) **เงินออกจากเว็บ** แสดงด้วยสีเขียว
`กำไร/ขาดทุน = เงินออกจากเว็บ − เงินเข้าเว็บ`

## สิทธิ์การใช้งาน

ระบบแยกสิทธิ์ออกเป็น **3 ชั้นอิสระจากกัน**

| ชั้น | เก็บที่ไหน | ใครเปลี่ยนได้ |
|---|---|---|
| **ผู้ดูแล** | env `LINE_ADMIN_USER_IDS` | แก้ที่การตั้งค่าเซิร์ฟเวอร์เท่านั้น เปลี่ยนผ่านหน้าเว็บไม่ได้ |
| **เข้าใช้งานได้** | คอลัมน์ `app_users.is_active` | ผู้ดูแล กดที่หน้า `/admin` |
| **เห็นข้อมูลทุกคน** | คอลัมน์ `app_users.can_view_all` | ผู้ดูแล กดที่หน้า `/admin` |

### คนใหม่เข้ามาแล้วเกิดอะไรขึ้น

1. ล็อกอิน LINE สำเร็จ → ระบบสร้างแถวใน `app_users` ให้ โดย `is_active = false`
2. เจอหน้า **"รอผู้ดูแลอนุมัติ"** ยังใช้งานอะไรไม่ได้
3. ผู้ดูแลเปิด `/admin` เห็นชื่อในกลุ่ม *รออนุมัติ* → กด **อนุมัติ**
4. คนนั้นกด *เช็คสถานะอีกครั้ง* แล้วใช้งานได้ทันที โดยเห็นเฉพาะข้อมูลของตัวเอง

### สิทธิ์ "เห็นทุกบัญชี"

ค่าเริ่มต้นคือ **เห็นเฉพาะของตัวเอง** — บัญชีของแต่ละคนแยกขาดจากกัน

เปิดสิทธิ์นี้ให้ใครแล้ว คนนั้นจะ

- ✅ เห็น **รายการ** และ **สรุปยอด** ของทุกคนรวมกัน (หน้ารายการจะบอกชื่อเจ้าของแต่ละแถว)
- ✅ เปิดดูรูปสลิปของทุกคนได้
- ❌ **แก้หรือลบรายการของคนอื่นไม่ได้** — ทุก endpoint ที่เขียนข้อมูลยังผูกกับ `owner_id` ของตัวเองเสมอ
- ❌ รายการที่บันทึกใหม่ยังเข้าบัญชีตัวเองตามปกติ

สิทธิ์นี้คุมเฉพาะ **ยอดเงิน** — ส่วน **รายชื่อเว็บ** ทุกคนเห็นและแก้ได้เหมือนกันหมดอยู่แล้ว

> ⚠️ **ตั้ง `LINE_ADMIN_USER_IDS` ให้เรียบร้อยก่อนรัน migration `0003`**
> ไม่งั้นคนที่เข้ามาใหม่จะค้างอยู่ที่หน้ารออนุมัติโดยไม่มีใครอนุมัติให้ได้
> (ผู้ดูแลถูกเปิดใช้งานอัตโนมัติทุกครั้งที่ล็อกอิน จึงล็อกตัวเองออกไม่ได้)

## สถาปัตยกรรม

```
LINE (rich menu / ลิงก์ LIFF)
        │
        ▼
  หน้าเว็บ Next.js (LIFF)  ── liff.getIDToken() ──┐
        │  อัปโหลดรูป (ย่อขนาดในเครื่องก่อน)      │
        ▼                                          ▼
  /api/ocr ─┬─ 1. ถอด QR ตรวจสอบสลิป (ในเครื่อง)  │  ทุก API ตรวจ ID token
        │     └─ 2. Google Cloud Vision (OCR)        │  กับ LINE ก่อนเสมอ
        ├── Supabase Storage (bucket "slips" แบบ private)
        ▼
  /api/transactions ──► Supabase Postgres (RLS เปิด ไม่มี policy)
        ▲
        │
  /api/summary ◄── /api/line/webhook (ตอบสรุปยอดในแชท)
```

- **ฐานข้อมูล** เปิด RLS ไว้และ *ไม่* สร้าง policy → anon key เข้าไม่ถึงข้อมูลเลย
  เว็บเข้าถึงผ่าน `service_role` key ฝั่ง server เท่านั้น และกรอง `owner_id` ของผู้ใช้ที่ผ่านการตรวจ token แล้วทุกครั้ง
- **รูปสลิป** เก็บใน bucket แบบ private เปิดดูผ่าน signed URL อายุ 5 นาที และเช็คว่า path ขึ้นต้นด้วย id ของเจ้าของเสมอ

## อ่าน QR บนสลิป

สลิปโอนเงินของธนาคารไทยมี **QR ตรวจสอบสลิป** พิมพ์ไว้มุมล่าง ข้างในเป็นข้อมูล TLV แบบเดียวกับ EMVCo
ถอดออกมาได้ตรง ๆ ด้วย `jsqr` + `sharp` โดยไม่ต้องเรียก API ใด ๆ — ไม่ใช่การอ่านตัวหนังสือ จึงไม่มีทางอ่านเพี้ยน

```
payload : 0041000600000101030040220016239094536DPP015375102TH910483DB
          └─ 00 ข้อมูลรายการ ─┬─ 01 = 004                (รหัสธนาคารต้นทาง = กสิกรไทย)
                              └─ 02 = 016239094536DPP01537 (เลขที่รายการ)
             51 = TH                                       (รหัสประเทศ)
             91 = 83DB                                     (CRC-16/CCITT ของทุกอย่างก่อนหน้า)
```

**ได้อะไร / ไม่ได้อะไร**

| ได้จาก QR แน่นอน | ต้องอ่านจากตัวหนังสือ (Vision) หรือกรอกเอง |
|---|---|
| เลขที่รายการ (`ref_no`) | ยอดเงิน |
| ธนาคารต้นทาง (`bank_name`) | วันที่และเวลา |
| ยืนยันว่าเป็นสลิปโอนเงินจริง → `direction = deposit` | ชื่อบัญชีปลายทาง |

**กติกาที่ใช้**

- ตรวจ **CRC** ทุกครั้ง ถ้าไม่ผ่านคือทิ้งทันที — เอาเลขที่รายการผิดไปใส่ฟอร์มอันตรายกว่าอ่านไม่ออก
- QR **ชนะเสมอ** เมื่อค่าไม่ตรงกับที่โมเดลอ่านจากตัวหนังสือ และจะขึ้นเตือนให้ตรวจยอดกับวันที่ซ้ำ
  เพราะถ้าโมเดลอ่านเลขที่รายการพลาด ค่าอื่นก็น่าสงสัยด้วย
- QR ที่ไม่ใช่ของสลิป (เช่น QR พร้อมเพย์รับเงิน) จะถูกปฏิเสธ ไม่เอามาปนกับเลขที่รายการ
- รูปที่ไม่มี QR (เช่นแคปหน้าจอถอนเงินจากเว็บ) ถือเป็นเรื่องปกติ ระบบข้ามไปใช้การอ่านตัวหนังสือแทน

**ความทนทาน** — ทดสอบกับสลิป K PLUS จริง ยังถอดได้ครบทุกกรณี ใช้เวลา 50–350 ms

| กรณี | ผล |
|---|---|
| ต้นฉบับ / PNG / WebP / ย่อเหลือ 1600px, 800px, 500px | อ่านออก |
| หมุน 90° · เอียง 6° | อ่านออก |
| ครอป QR ทิ้ง · รูปไม่มี QR · ไฟล์เสีย | คืน `null` ไม่ล้ม |

## ลำดับการอ่านรูป

อ่านสองชั้น ชั้นแรกฟรีและแม่นกว่า จึงชนะเสมอเมื่อค่าชนกัน

| ชั้น | อ่านอะไร | ค่าใช้จ่าย |
|---|---|---|
| 1. QR ตรวจสอบสลิป | เลขที่รายการ, ธนาคารต้นทาง, ยืนยันว่าเป็นสลิปจริง | ฟรี (ทำในเครื่อง) |
| 2. Google Cloud Vision | ยอดเงิน, วันเวลา, ทิศทาง (เข้า/ออก), ชื่อเว็บ | 1,000 ภาพ/เดือนแรกฟรี |

**ทำไมไม่ใช้ Vision อย่างเดียว** — Vision อ่านเลขที่รายการได้ก็จริง แต่เป็นสตริง 20 ตัวอักษร
ปนตัวเลขกับตัวอักษร ซึ่งเป็นจุดที่ OCR พลาดง่ายที่สุด (0 กับ O, 1 กับ I) และเลขนี้คือกุญแจที่ใช้
**กันบันทึกสลิปซ้ำ** อ่านพลาดตัวเดียว = จับใบซ้ำไม่ได้ = ยอดเงินซ้ำในบัญชี
ส่วน QR ถอดออกมาตรง ๆ พร้อม CRC ให้ตรวจ จึงไม่มีทางเพี้ยน และไม่มีค่าใช้จ่ายเพิ่ม (~200 ms)

- ผลลัพธ์บอกไว้ใน `ocr.sources` ว่าผ่านชั้นไหนมาบ้าง เช่น `["qr", "vision"]`
- **QR ชนะเสมอ** สำหรับเลขที่รายการและธนาคาร ถ้าค่าไม่ตรงกันจะขึ้นเตือนให้ตรวจยอดกับวันที่ด้วย
- Vision ล่มหรือโควตาหมด **ไม่ทำให้ทั้งคำขอพัง** — ค่าที่ได้จาก QR ยังถูกส่งกลับไปพร้อมข้อความเตือน
- อ่านไม่ครบไม่ใช่ทางตัน ฟอร์มให้กรอกยอดกับวันที่เองได้อยู่แล้ว จึงไม่ต้องมีตัวสำรองที่มีค่าใช้จ่าย
- การแยกฟิลด์ออกจากข้อความอยู่ใน `slip-text.ts` แยกจากตัวเรียก API จึงเปลี่ยนตัว OCR ข้างหลังได้
  และทดสอบได้โดยไม่ต้องต่อเน็ตด้วย `npx tsx scripts/parser-check.ts` (มีข้อความจริงจาก Vision เป็นเคสไว้แล้ว)
  โดยไม่ต้องแก้ตรรกะ และทดสอบด้วยข้อความดิบได้โดยไม่ต้องต่อเน็ต

**กติกาการอ่านยอดเงิน** — หยิบเฉพาะตัวเลขที่อยู่กับป้าย *จำนวน / จำนวนเงิน / ยอดถอน*
และตัดตัวเลขข้างป้าย *ค่าธรรมเนียม / ยอดคงเหลือ / เครดิตคงเหลือ / โบนัส* ทิ้งเสมอ
วันที่จับทีละบรรทัด (ไม่ใช่ทั้งก้อน) แล้วตรวจว่าอยู่ในช่วง 10 ปีย้อนหลังถึงพรุ่งนี้
เพื่อไม่ให้เลขอ้างอิงยาว ๆ ถูกอ่านเป็นวันที่

## อัปโหลดหน้าเว็บคู่กับสลิป

สลับไปโหมด **"หน้าเว็บ + สลิป"** ในหน้าบันทึกรายการ แล้วเลือกรูปทีเดียวหลายใบ
ระบบทำให้เองสามขั้น: **แยกประเภท → จับคู่ → รวมเป็นรายการ**

**ภาพสองแบบบอกคนละอย่าง เอามารวมกันถึงจะครบ**

| | ภาพหน้าฝาก/ถอนของเว็บ | สลิปธนาคาร |
|---|---|---|
| เว็บไหน | โดเมนที่มุมล่าง เช่น `chokddd365.run` | ไม่มี |
| บัญชีที่โอนออก / ปลายทาง | มีครบ ทั้งธนาคาร เลขบัญชี และชื่อเจ้าของ (บางหน้ามีแค่ฝั่งของเว็บ) | มีทั้งสองฝั่ง แต่เลขบัญชีถูกปิดบังบางส่วน (`703-0-xxx755`) |
| ยอดเงิน | ยอดที่ "แจ้งไว้" | ยอดที่โอนจริง — ใช้ยอดนี้เป็นหลัก |
| วันเวลา | หน้าแจ้งโอนมีแต่เวลา ส่วนหน้ารายการฝาก-ถอนมีวันที่ครบ | มีครบ — ใช้ค่านี้เป็นหลัก |
| เลขที่รายการ | รหัสของเว็บ (`QR-2737703011042845`) | เลขที่รายการจาก QR ตรวจสอบสลิป |

**แยกประเภท** — ถอด QR ได้ = สลิปแน่นอน ที่เหลือดูจากคำบนภาพ (`โอนจากบัญชีนี้เท่านั้น`,
`โอนถึงบัญชี`, `ชั่วโมงที่โอนเงิน`, โดเมน) เทียบกับคำที่มีแต่บนสลิป (`โอนเงินสำเร็จ`, `ค่าธรรมเนียม`)
ผู้ใช้ระบุเองได้ตอนกดปุ่ม "เพิ่มหน้าเว็บ / เพิ่มสลิป" ในคู่ที่ยังไม่ครบ

**จับคู่** — ให้คะแนนทุกคู่ที่เป็นไปได้ แล้วหยิบคู่คะแนนสูงสุดก่อน

| สัญญาณ | คะแนน |
|---|---|
| ยอดเงินตรงกัน | +100 (ไม่ตรง −60) |
| เวลาห่างกันไม่เกิน 1 ชั่วโมง | +0 ถึง +30 ตามความห่าง |
| ธนาคารของบัญชีเราตรงกับธนาคารต้นทางบนสลิป | +12 |
| ลำดับที่เลือกไฟล์มาใกล้กัน | +0 ถึง +6 |

รอบแรกจับเฉพาะคู่ที่มั่นใจ (≥ 20) รอบสองจับที่เหลือแบบเดาให้พร้อมติดคำเตือน
ที่เหลือจริง ๆ ขึ้นเป็นรายการเดี่ยว — กด "จับคู่กับรายการอื่น" หรือ "แยกคู่" เองได้ โดยไม่ต้องอัปโหลดใหม่
(ตรรกะการจับคู่อยู่ฝั่งเบราว์เซอร์ทั้งหมด สลับคู่จึงไม่เสียโควตา Vision เพิ่ม)

**รวมเป็นรายการ** — ค่าที่ขัดกันจะเลือกฝั่งที่เชื่อถือได้มากกว่าเสมอ แล้วขึ้นคำเตือนให้ตรวจ

- ยอดเงินและวันเวลา → เอาจาก **สลิป**
- ชื่อเว็บ บัญชีที่โอนออก/ปลายทาง → เอาจาก **หน้าเว็บ**
- `bank_name + account_no + account_name` = บัญชีของเรา (ฝาก = ฝั่งที่โอนออก, ถอน = ฝั่งที่รับเงิน)
- `counterparty_bank + counterparty_account_no + counterparty` = บัญชีของเว็บ
- หน้าเว็บบอกบัญชีไม่ครบ (เช่นหน้ารายการที่โชว์แต่บัญชีเว็บ) ก็เติมจากฝั่ง "จาก/ไปที่" บนสลิปให้
- ชื่อเว็บเลือกจากโดเมนก่อน (คอลัมน์ `sites.domain`) ไม่เจอค่อยเทียบกับชื่อเว็บที่มีอยู่
  ยังไม่มีเว็บนั้นในระบบ ระบบจะ **เพิ่มเว็บให้อัตโนมัติจากโดเมน** (`kindee365.com` → เว็บชื่อ `kindee365`)
  แล้วเลือกให้เลย เปลี่ยนชื่อ/สี/อิโมจิทีหลังได้ที่หน้าจัดการเว็บ

**ค่าใช้จ่าย** — หนึ่งคู่ = สองภาพ = **2 หน่วยของ Vision** (หน้าเว็บไม่มี QR ให้ถอด ต้องอ่านตัวหนังสือล้วน)
ส่วนการจับคู่ การสลับคู่ และการรวมค่า ทำในเบราว์เซอร์ ไม่มีค่าใช้จ่ายเพิ่ม

ทดสอบกติกาทั้งหมดโดยไม่ต้องต่อเน็ต: `npx tsx scripts/pair-check.ts`
ดูว่าภาพจริงอ่านออกแค่ไหน: `npx tsx scripts/ocr-smoke.ts ./หน้าเว็บ.jpg` (พิมพ์ข้อความดิบจาก Vision ให้ดูด้วย)

## ติดตั้ง

### 1. Supabase

1. สร้าง project ใหม่ (แนะนำ region `Southeast Asia (Singapore)`)
2. เปิด **SQL Editor** แล้วรันไฟล์ใน `supabase/migrations/` ให้ครบ **เรียงตามเลขไฟล์**
   - `0001_init.sql` ตารางหลัก + bucket
   - `0002_seed_sites.sql` รายชื่อเว็บตั้งต้น (แก้ชื่อได้ตามใจ)
   - `0003` – `0006` อนุมัติสมาชิก, สิทธิ์ดูข้ามบัญชี, อิโมจิประจำเว็บ, รายชื่อเว็บส่วนกลาง
   - `0007_slip_pairs.sql` ช่องเก็บภาพหน้าเว็บ + เลขบัญชีสองฝั่ง + โดเมนของเว็บ
     (ยังไม่รันก็ใช้งานส่วนอื่นได้ แต่โหมด "หน้าเว็บ + สลิป" จะเก็บได้แค่ยอดกับรูปสลิป)
3. ตรวจว่ามี bucket ชื่อ `slips` แบบ **private** ในเมนู Storage
   (migration สร้างให้แล้ว ถ้าไม่ขึ้นให้กด New bucket แล้วตั้งชื่อ `slips` โดยไม่ติ๊ก Public)
4. คัดลอกค่าจาก **Project Settings → API**
   - `Project URL` → `NEXT_PUBLIC_SUPABASE_URL`
   - `service_role` key → `SUPABASE_SERVICE_ROLE_KEY` (ห้ามเอาไปใส่ฝั่ง client)

> ถ้าใช้ Supabase CLI: `supabase db push` จะรัน migration ให้อัตโนมัติ

### 2. LINE Login + LIFF (จำเป็น — ใช้ล็อกอินและกรอกฟอร์ม)

1. เข้า [LINE Developers](https://developers.line.biz/console/) → สร้าง Provider → สร้าง channel แบบ **LINE Login**
2. แท็บ **Basic settings** → คัดลอก `Channel ID` → `LINE_LOGIN_CHANNEL_ID`
3. แท็บ **LIFF** → **Add**
   - Endpoint URL: `https://<โดเมนของคุณ>/`
   - Size: `Full`
   - Scopes: ติ๊ก **profile** และ **openid** (ต้องมี openid ไม่งั้นจะไม่ได้ ID token)
4. คัดลอก `LIFF ID` → `NEXT_PUBLIC_LIFF_ID`

### 3. LINE Messaging API (ไม่บังคับ — ใช้ดูสรุปยอดในแชท)

1. สร้าง channel แบบ **Messaging API** เพิ่ม
2. `Channel secret` → `LINE_MESSAGING_CHANNEL_SECRET`
3. ออก `Channel access token (long-lived)` → `LINE_MESSAGING_CHANNEL_ACCESS_TOKEN`
4. ตั้ง **Webhook URL** = `https://<โดเมนของคุณ>/api/line/webhook` แล้วเปิด *Use webhook*
5. ปิด *Auto-reply messages* และ *Greeting messages* เพื่อไม่ให้ตอบชนกัน
6. (แนะนำ) ทำ Rich menu ปุ่มเดียวชี้ไปที่ `https://liff.line.me/<LIFF_ID>`

### 4. Google Cloud Vision (ใช้อ่านตัวหนังสือบนรูป)

1. สร้างโปรเจกต์ใน [Google Cloud Console](https://console.cloud.google.com/)
2. เปิดใช้ **Cloud Vision API**
3. *APIs & Services → Credentials → Create credentials → API key*
4. จำกัด key ให้เรียกได้เฉพาะ Cloud Vision API แล้วใส่ใน `GOOGLE_VISION_API_KEY`

โควตา **1,000 ภาพแรกต่อเดือนฟรี ไม่มีวันหมดอายุ** หลังจากนั้นคิดตามจำนวนภาพ
(หนึ่งอัปโหลด = หนึ่งภาพ ขนาดไฟล์ไม่มีผลต่อราคา)

> ถ้าไม่ใส่ key ระบบยังใช้ได้ปกติ และยังถอดเลขที่รายการกับธนาคารจาก QR ให้อยู่ดี
> เหลือแค่ยอดเงินกับวันที่ที่ต้องพิมพ์เอง

### 5. รันในเครื่อง

```bash
cp .env.example .env.local     # แล้วเติมค่าให้ครบ
npm install
npm run dev
```

อยากทดสอบโดยไม่ผ่าน LINE ให้ตั้งใน `.env.local`

```
DEV_AUTH_BYPASS=true
NEXT_PUBLIC_DEV_LINE_USER_ID=Utest0001
```

แล้วเปิด http://localhost:3000 ได้เลย (สวิตช์นี้ทำงานเฉพาะตอนไม่ใช่ production)

ทดสอบการอ่านรูปแยกเดี่ยว ๆ

```bash
npx tsx scripts/ocr-smoke.ts ./slip.jpg                             # ถอด QR อย่างเดียว ไม่เรียก API
GOOGLE_VISION_API_KEY=... npx tsx scripts/ocr-smoke.ts ./slip.jpg   # เส้นทางจริง QR + Vision
```

## Deploy

โปรเจกต์เป็น Next.js มาตรฐาน ไม่ผูกกับผู้ให้บริการรายไหน

**Vercel** — import repo แล้วใส่ environment variables ทั้งหมด กด deploy

**Netlify** — ใช้ `@netlify/plugin-nextjs` (Netlify ตรวจเจอ Next.js ให้อัตโนมัติ)
build command `npm run build` / publish directory `.next`

**Docker**

```bash
docker build -t lotto-accounting \
  --build-arg NEXT_PUBLIC_SUPABASE_URL=https://xxx.supabase.co \
  --build-arg NEXT_PUBLIC_LIFF_ID=1234567890-abcdefgh \
  --build-arg NEXT_PUBLIC_APP_URL=https://your-domain \
  .
docker run -p 3000:3000 --env-file .env.local lotto-accounting
```

> ค่า `NEXT_PUBLIC_*` ถูกฝังตอน build — ถ้าเปลี่ยนต้อง build ใหม่

หลัง deploy แล้วอย่าลืมกลับไปแก้ **Endpoint URL ของ LIFF** และ **Webhook URL** ให้ตรงกับโดเมนจริง

## หมายเหตุ

- **จำกัดคนใช้** ตั้ง `LINE_ALLOWED_USER_IDS` เป็น LINE userId คั่นด้วย comma
  ถ้าไม่ตั้ง ใครล็อกอินก็ใช้ได้ แต่ข้อมูลของแต่ละคนแยกขาดจากกันอยู่แล้ว
- **โซนเวลา** ตัดยอดตาม `Asia/Bangkok` ทั้งระบบ (คอลัมน์ `occurred_date` ในฐานข้อมูลก็ยึดโซนนี้)
- **ไฟล์ค้าง** รูปที่อัปโหลดแล้วผู้ใช้ไม่กดบันทึกจะค้างอยู่ที่ `<user-id>/tmp/` ใน bucket
  ลบทิ้งเป็นระยะได้ตามสะดวก (ไฟล์ที่บันทึกแล้วจะถูกย้ายไปโฟลเดอร์ตามเดือน)
- **ขนาดไฟล์รูป** หน้าเว็บย่อรูปให้เหลือด้านยาวสุด 1600px ก่อนอัปโหลดอยู่แล้ว (ปกติไม่ถึง 1 MB)
  ฝั่ง server จำกัดไว้ที่ 8 MB แต่ถ้า deploy บน serverless บางเจ้าจะจำกัด request body ราว 4.5 MB — ยังเหลือที่เหลือเฟือ
- **ค่าใช้จ่ายการอ่านรูป** ปรับได้ที่ `OCR_MODEL` และ `OCR_EFFORT` ใน env
- ยอดที่อ่านได้จากรูป **ควรตรวจก่อนกดบันทึกทุกครั้ง** — หน้าฟอร์มจะแสดงระดับความมั่นใจและคำเตือนไว้ให้
